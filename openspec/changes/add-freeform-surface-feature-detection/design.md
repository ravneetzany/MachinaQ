## Post-implementation correction (found via live FreeCAD re-test)

After this change shipped, the user re-tested the exact selection that surfaced it, and the FreeCAD addon's correlation panel *still* matched a distant conical primitive instead of the newly-added `elongated_boss`/`freeform` features. Root cause: `freeform` primitives' `details` carried `long_extent`/`short_extent` but never any `axis_px`/`axis_py`/`axis_pz` position keys — `face_correlation.py`'s `_primitive_position()` (in the already-shipped `add-freecad-cam-integration` addon) requires those keys and silently `continue`s past any primitive missing them, so every `freeform` primitive was structurally invisible to the correlation search regardless of proximity, no matter how good the operation classification became. Fixed by adding `StepTextParser.get_face_centroid()` (a plain average of a face's boundary vertices, reusing the same `_face_vertices()` already used for extents) and having `pipeline.py`'s `freeform` branch store it as `axis_px`/`py`/`pz` — deliberately with no `axis_dx`/`dy`/`dz`, since a free-form face has no single direction; `face_correlation.py` already treats a point-only primitive as point-distance-only, which is exactly the right fallback here, so no addon-side change was needed.

**Known remaining limitation after the centroid fix, then addressed with a second fix (user asked for it)**: a vertex-average centroid is a crude position for a *large* free-form patch — re-verified against the real fixture that surfaced this change, the nearest `freeform` primitive to the actual click point was still ~14.8mm away (vs. ~4.6mm for the conical primitive that matched), because the patch's own boundary-vertex average can sit far from whichever specific point on its surface was clicked. Given the choice between leaving this as a documented limitation (same "approximate, not exact" framing already used throughout this project) or improving it, the user asked for the improvement. Fixed by adding `StepTextParser.get_face_boundary_points()` (the face's *distinct* boundary vertices, deduplicated — reusing `_face_vertices()` again) and storing them as `details["boundary_points"]` (a list of `[x, y, z]` triples) alongside the existing single centroid, for `freeform` primitives only. `face_correlation.py`'s `nearest_primitive()` now takes the minimum distance over both the centroid and every boundary point when `boundary_points` is present — strictly additive (primitives without it are unaffected, verified by a dedicated test), and still no NURBS surface evaluation attempted (Non-Goals, below) — just checking more candidate points instead of one. Re-verified against the real fixture: the same selection that previously matched a conical primitive 4.63mm away now matches the actual `freeform` primitive at 3.29mm.

## Context

`src/parser.py`'s `_parse_entities()` splits STEP file content on `;` (correctly handling multi-line entities at the split level, since STEP entities terminate with `;` regardless of embedded newlines) but then matches each candidate entity string with `re.match(r'#(\d+)\s*=\s*([A-Z0-9_]+)\s*\((.*)\)', line)` — no `re.DOTALL`. `.` does not match `\n` by default, so this regex silently fails on any entity whose attribute list contains embedded newlines, and the entity is never added to `self.entities`. Directly confirmed on the STEP file that surfaced this change: 0/88 `B_SPLINE_SURFACE_WITH_KNOTS` entities parsed before the fix, 88/88 after adding `re.DOTALL`. `TOROIDAL_SURFACE` entities in the same file are single-line and already parse correctly (36/36) — their only gap is `_extract_primitives()` never dispatching on that entity type.

`_build_topology()` (adjacency, face↔edge maps) does not depend on an `ADVANCED_FACE`'s surface entity resolving — `face_edges[fid]` is built purely from `EDGE_LOOP`/`ORIENTED_EDGE`/`EDGE_CURVE` references, independent of surface type. `face_surface[fid] = self.entities[sid].type` is skipped only when `sid not in self.entities` — meaning before this change's regex fix, a `B_SPLINE_SURFACE_WITH_KNOTS`-surfaced face still had valid adjacency/vertex data internally, but `get_face_surface_types()` never reported its actual surface type, and `_extract_primitives()` had no matching entity to iterate over regardless. The regex fix is a prerequisite for everything else in this change: without it, `B_SPLINE_SURFACE_WITH_KNOTS` entities cannot be dispatched on at all, since they're absent from `self.entities`.

`get_face_bounding_extents(face_id, normal=None)` is already surface-agnostic — it walks `_face_vertices()` (also surface-independent) and falls back to a raw 3D axis-aligned bounding box's two largest axes when no `normal` is given. This is exactly the fallback path free-form faces need, and it required no changes to reuse.

`operation_classifier.classify_feature()`'s STEP-path (`principal_axis=None`, per existing decision 2 elsewhere in this project's history) branches in `_classify_without_axis()` purely on primitive `type` (`ptypes = {p.type for p in prims}`), never on `feature.feature_type`. Today, `cylindrical`/`conical` primitive types unconditionally return `DRILLING` in that path — including for the existing `boss` feature type, whose primitives are `cylindrical`/`conical`. This is a pre-existing conflation (a boss, a protrusion, reported as needing "drilling") this change does not fix — see Non-Goals.

## Goals / Non-Goals

**Goals:**
- Fix the multi-line STEP entity parsing bug so no entity type (not just the two this change targets) is silently dropped when its attributes span multiple lines.
- Give `TOROIDAL_SURFACE` and `B_SPLINE_SURFACE_WITH_KNOTS` faces geometric primitive representations, using only data already resolvable by existing helpers (axis placement resolution for toroidal, bounding extents for free-form) — no NURBS control-point/knot-vector math.
- Recognize elongated curved protrusions (built from these new primitive types, or from `cylindrical` primitives that don't meet the existing `boss` rule's `adjacent_planar_count == 1` topology) as an `elongated_boss` feature, reaching operation classification instead of being unclassified or (for free-form faces, before this change) invisible entirely.
- Give `toroidal`/`freeform` primitives a required-operation determination in the primitive-type-only classification path.

**Non-Goals:**
- Exact NURBS surface evaluation (control points, knot vectors, degree) — `freeform` primitives carry only bounding-extent data, deliberately, per proposal.md's What Changes.
- Distinguishing a true convex protrusion from a concave pocket sharing the same topology/extent signature — the existing `detect_bosses()` docstring already documents this as an unsolved limitation for regular bosses; `elongated_boss` inherits the same limitation and does not attempt to solve it.
- Fixing the pre-existing `cylindrical`/`conical`-primitive-type → `DRILLING` conflation for the existing `boss` feature type (Context, above) — out of scope; this change only adds correct classification for the *new* `toroidal`/`freeform` types, and reuses `cylindrical` only as an additional elongation-evidence source for `elongated_boss`, not as a fix to existing `boss` behavior.
- Any FreeCAD addon changes — the addon's report rendering already displays whatever `features`/`operations_summary` the API returns.

## Decisions

**1. Regex fix: add `re.DOTALL` to `_parse_entities()`'s entity-matching regex.**
The simplest, most localized fix for the multi-line parsing bug (Context). Alternative considered: pre-strip newlines from `attributes_str` after a non-DOTALL match on just the `#id = TYPE(` prefix (rejected — more invasive, and the failure is in matching the *whole* entity, prefix included, not in a downstream step). `re.DOTALL` only changes what `.` matches within this one regex; nothing else in `_parse_entities()`/`_parse_attributes()` depends on newline-sensitive matching, so this is a narrow, low-risk change with a broad correctness benefit (fixes this for *any* multi-line entity type, not just the two this change adds support for).

**2. `TOROIDAL_SURFACE` extraction mirrors `CONICAL_SURFACE` exactly: axis placement + two radii.**
`TOROIDAL_SURFACE('name', #axis2_placement_3d, major_radius, minor_radius)` — the same shape `CONICAL_SURFACE`'s `radius`/`semi_angle` pair already resolves via `_resolve_placement(attrs[1])`. `GeometryPrimitives` gains a `toroids: List[Tuple[int, float, float, Vector3, Vector3]]` field (surface id, major radius, minor radius, axis point, axis direction), and `pipeline.py`'s `_extract_primitives()` builds `SurfacePrimitive(type="toroidal", details={"major_radius": ..., "minor_radius": ..., **axis_to_details(...)})` entries, reusing `axis_to_details()` exactly as cylinders/cones already do — no new storage convention.

**3. `B_SPLINE_SURFACE_WITH_KNOTS` extraction stores only `(surface_id,)` plus whichever face(s) reference it; primitive `details` come entirely from `get_face_bounding_extents(face_id, normal=None)` at `SurfacePrimitive`-build time — the same pattern `PLANE` already uses for `long_extent`/`short_extent`.**
No attempt to parse the entity's own nested attribute structure (control point grid, u/v degrees, knot vectors) — proposal.md's explicit scope boundary. Since a free-form face has no single normal, `get_face_bounding_extents()` is called with `normal=None`, using its existing raw-3D-bounding-box fallback (already implemented, not new code). `GeometryPrimitives` gains a `freeforms: List[int]` field (surface ids only); `pipeline.py` resolves extents per `get_surface_face_ids(surf_id)` face, matching the existing per-plane loop structure exactly (`for fid in self.parser.get_surface_face_ids(surf_id): extents = ...; break`).

**4. `elongated_boss` detection: bounding-extent aspect ratio, over `toroidal`/`freeform`/`cylindrical` primitives not already claimed, claimed last (after slots and `planar_face`).**
Reuses the exact aspect-ratio evidence shape `detect_slots()` already established (`SLOT_ASPECT_RATIO_THRESHOLD`-style: `long_extent / short_extent` at or above a threshold), but without `detect_slots()`'s adjacent-face-count band (`SLOT_MIN_ADJACENT_FACES`/`SLOT_MAX_ADJACENT_FACES`) — that band exists specifically to bound a *pocket's* wall count, which has no equivalent meaning for a curved protrusion's face count. `cylindrical` primitives are included as an elongation-evidence source (not just `toroidal`/`freeform`) because a swept arm can legitimately be represented as a large-radius `CYLINDRICAL_SURFACE` in STEP (constant circular curvature), and today such a face, if it doesn't happen to have `adjacent_planar_count == 1`, falls through `detect_bosses()` entirely with no fallback — `elongated_boss` is claimed only from primitives *remaining* after `detect_bosses()`/`detect_slots()`/`detect_faces()` have already run, so this never double-claims a face the existing `boss` or `planar_face` rules already matched. Cylindrical/toroidal primitives use their own `long_extent`/`short_extent` if present (not currently computed for them — see Open Questions) or fall back to axis-length-derived elongation evidence; free-form primitives use their `long_extent`/`short_extent` from decision 3 directly.

**5. Operation classification: `toroidal` gets axis-alignment-based 3-axis/5-axis (like the existing planar/cylindrical pattern); `freeform` always gets 5-axis in the no-principal-axis path.**
`toroidal` primitives retain real axis data (decision 2), so `_classify_without_axis()` can reuse the same `is_axis_aligned_with_any(direction)` check `_classify_with_axis()`'s planar branch already uses: axis-aligned → `THREE_AXIS_MILLING`, otherwise → `FIVE_AXIS_MILLING`. `freeform` primitives carry no axis data at all by design (decision 3) — there is no directional evidence to check, so they unconditionally get `FIVE_AXIS_MILLING`, matching proposal.md's stated default ("favoring 5-axis milling by default for genuinely free-form curvature, 3-axis only when there's clear evidence the surface is reachable along one axis" — free-form primitives here never carry that evidence).

## Risks / Trade-offs

- **[Risk]** The `re.DOTALL` regex fix changes parsing behavior for every multi-line entity in every STEP file this parser processes, not just the two types this change targets — a latent bug already existed everywhere, so this could surface previously-invisible entities (of other types) in existing fixtures' primitive/feature counts. → **Mitigation**: task list includes running the full existing test suite (including STEP fixture-based pipeline/parser tests) after this fix alone, before adding any of the new primitive types, to isolate and review any count changes it alone causes.
- **[Risk]** `elongated_boss`'s aspect-ratio-only evidence, like `detect_slots()`'s, cannot distinguish a genuine protrusion from a concave feature with the same extent signature (Non-Goals) — a curved pocket could theoretically be misclassified the same way. → **Mitigation**: this is an accepted, already-documented limitation carried forward from `detect_bosses()`, not newly introduced; the feature's rationale string and the FreeCAD addon's "approximate match" labeling (existing, unrelated-to-this-change UI text) keep this visible rather than silently authoritative.
- **[Risk]** `toroidal`/`cylindrical` primitives contributing to `elongated_boss` may lack `long_extent`/`short_extent` (only `freeform`/`planar` primitives compute those today) — the detection rule needs a defined fallback (e.g. treating a large-radius cylindrical/toroidal face with no extent data as inconclusive, same as `detect_slots()`'s existing missing-data guard) rather than erroring. → **Mitigation**: task list requires an explicit test for this case; see Open Questions for whether `long_extent`/`short_extent` computation should be extended to non-planar primitives as part of this change or deferred.

## Open Questions

- Should `get_face_bounding_extents()`-style extent computation be extended to `cylindrical`/`toroidal` primitives directly (today it's only wired up for `planar`/`freeform`), or is axis-length/adjacency-only evidence sufficient for `elongated_boss` on those two types for now? This affects decision 4's exact implementation but not the specs, the chosen approach's shape, or the task breakdown at a high level — deferred to task-level implementation judgment, informed by whichever real fixture data is available when task 1 is implemented.
